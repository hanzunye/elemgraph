# Q1 for BFS on the Apple M2, 2026-11-04

First full run of `bench/bfs.cpp`. Raw results: [`2026-11-04.json`](2026-11-04.json).

## Setup

- Apple M2 (4 performance + 4 efficiency cores, 16 GB), macOS, on AC power, no other
  applications in use. QoS class `USER_INTERACTIVE`; macOS offers no core pinning and no fixed
  clock (DESIGN.md §6).
- clang 21.1.8 with libc++, `-O3 -DNDEBUG`, commit `1c746ea`.
- `elemgraph_bench --benchmark_repetitions=10 --benchmark_report_aggregates_only=true`: the table
  shows medians of 10 repetitions. The coefficient of variation is at most 2.2 %, except
  G(n,m) with 2^12 vertices on `csr_graph` (11 %).
- `mhz_per_cpu: 24` in the JSON is the timer frequency that Google Benchmark finds on Apple
  silicon, not the CPU clock.

## Reading

1. CSR is faster in every case, but mostly by only 5–24 %.
2. For G(n,m) and R-MAT the gap is not monotone in the size: 1.86× with 2^20 vertices, then
   1.09–1.12× with 2^22. A rerun of the 2^20 cases alone, in a fresh process, gave 1.83× and
   1.79×, so the peak is not caused by memory left over from the previous graph.
   A guess, not yet checked: with 2^20 vertices the per-vertex arrays of the search (distance
   and parent, 8 MB) still fit in the 16 MB L2 of a performance core, so the adjacency list's
   extra load per vertex (the vector header, then its data) is what misses. With 2^22 vertices
   these arrays take 32 MB, and the random accesses to `distance[w]` miss for both
   representations and dominate. Checking this needs hardware counters (`perf stat` on the x86
   laptop) and the sizes in between (2^19, 2^21).
3. On the grid the gap stays at 1.05–1.16× for all sizes: neighbours have nearby ids, so both
   representations read memory almost sequentially.
4. `std::queue` costs 3–33 % more than the flat array; the one exception (0.97, G(n,m) 2^12) is
   the run with the 11 % variation.

## Caveats

- One machine and one run so far; the x86 laptop with a pinned core and a fixed clock comes next.
- Each vector of the adjacency list is reserved to its degree and the vectors are allocated in
  vertex order, so the list is about as compact as a vector of vectors gets. Lists built with
  plain `push_back` may be more scattered; that was not measured.
