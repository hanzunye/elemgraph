# Q6 on the Apple M2, 2026-11-22

This is the first run of `bench/certifying.cpp` (Q6 in [`docs/DESIGN.md`](../../../docs/DESIGN.md):
what do producing and checking a certificate cost compared with the plain test?). Raw results are
in [`2026-11-22.json`](2026-11-22.json).

## Setup

- Machine and settings as on [2026-11-04](2026-11-04.md): Apple M2, on AC power, no other
  applications open, QoS class `USER_INTERACTIVE`.
- clang 21.1.8 with libc++, `-O3 -DNDEBUG`, commit `ed1cc91`.
- `bench/run.sh m2 --benchmark_filter=certifying/`: 10 repetitions of each benchmark. All tables
  show medians. The run took 36 minutes.
- Variation within the run: with 2^14 vertices and more, the coefficient of variation is at most
  3.8 %, with one exception: certifying 2-vertex-connectivity on the grid with 2^21 vertices,
  14.7 %. Its median is in line with the neighbouring sizes. With 2^12 vertices it reaches 7.0 %.
  Checking the G(n,m) certificates takes less than 50 µs and varies by up to 12.8 %.
- Variation between runs: *DFS* and *Plain* run the same code as *DFS* and *Chains* in the Q4 run
  of [2026-11-11](2026-11-11.md); `connectivity.hpp` and `dfs.hpp` have not changed since. With
  2^14 vertices and more, the DFS times agree within 1 % on the grid and within 3.1 % on G(n,m).
  The plain test agrees within 1 % on G(n,m), but is 2.6–4.0 % slower on the grid at every size.

## The inputs and their certificates

- **grid** and **G(n,m) + cycle** (`gnm_cycle`: the G(n,m) graph plus a Hamiltonian cycle) are
  2-vertex-connected. Both answers are yes, and both certificates are the m − n + 1 chains, as an
  ear decomposition (2-edge) or an open one (2-vertex).
- **G(n,m)** has bridges, so both answers are no. From 2^14 vertices on, it also has isolated
  vertices (5 with 2^14 vertices, 1,373 with 2^22). The graph is then disconnected, and both
  certificates are a smallest component: a single isolated vertex. With 2^12 vertices the graph is
  connected, and the certificates are a vertex of degree 1: one edge leaves it, and its neighbour
  separates it from the rest. So this run measures checking a "no" certificate only in its easiest
  case.

## Q6: certifying vs. the plain test

All parts start from the same `dfs()` result on the same `csr_graph`.
- *DFS* is the time of that search alone.
- *Plain* is `chain_connectivity()` without keeping the chains: the test without a certificate.
- *Certify* is `certify_two_edge_connectivity()` or `certify_two_vertex_connectivity()`: the same
  chain decomposition, with the chains kept and turned into a certificate.
- *Check* is `check_two_edge_connectivity()` or `check_two_vertex_connectivity()` on that
  certificate. The checkers use only the graph and the certificate, not the search.

### Reading

The ranges below are for 2^14 vertices and more.

1. **Producing a certificate costs 1.22–1.55× the plain test, DFS included.**
   - On the grid, the whole certifying test takes 1.22–1.27× as long as the plain test for
     2-edge-connectivity and 1.28–1.32× for 2-vertex-connectivity, at every size.
   - On the two random classes it takes 1.24–1.34× up to 2^16 vertices, rises to about 1.5× at
     2^19, and falls to 1.32–1.34× at 2^22.
   - After the search alone, the certifying test takes 1.49–2.16× as long as the plain test.

   On the random classes, this ratio is highest at 2^19 and 2^20 vertices, the sizes of the Q1
   peak on this machine. Nothing here explains that yet.
2. **Certifying 2-vertex-connectivity costs a little more than 2-edge-connectivity when the
   answer is yes.** After the search, it takes 7–8 % longer on the grid and 1–5 % longer on
   G(n,m) + cycle. To rule out a cycle that starts at a cut vertex, it looks at the first and last
   vertex of every chain after the first. On G(n,m) the answer is no and is found before that
   step, so the two take the same time.
3. **Where the extra time goes: a guess, partly checked.** The certifying tests run the same
   chain decomposition as the plain test, and two things come on top.
   - They store every chain: its start, its vertices and its edge ids. With 2^22 vertices on
     G(n,m) + cycle, these are 16.8 million chains, and their contents take 369 MB. The CSR graph
     itself takes 352 MB.
   - For each tree edge on a chain, they find its id by scanning the list of its lower end for
     the parent (`detail::tree_edge()`). The plain test only reads the state and the parent of
     that vertex.

   A quick check outside the benchmark suite measured each part separately. It used a copy of
   `chain_connectivity()` in a throwaway program, built with the same compiler and flags, on the
   same graphs. Each value is the minimum of 21 runs, or 7 with 2^20 vertices, from a single
   run of the program. The values are times relative to the plain test, on G(n,m) + cycle:

   | log2 n | Keeping the chains | Without the scan (edge id 0) | The scan only, nothing stored |
   |-------:|-------------------:|-----------------------------:|------------------------------:|
   | 14 | 1.62 | 1.30 | 1.35 |
   | 16 | 1.56 | 1.27 | 1.30 |
   | 18 | 2.06 | 1.65 | 1.41 |
   | 20 | 2.07 | 1.55 | 1.53 |

   Storing and scanning each add about half of the extra time, and the two parts add up to the
   whole within 0.03. The program's grid values are left out: its first measurement, the plain
   test on the grid with 2^16 vertices, took more than twice as long as in the benchmark.

   Both parts can be made cheaper.
   - `dfs()` reaches each vertex through its tree edge. If it recorded that edge's id, the scan
     would become a single array read.
   - The chain starts are stored as 64-bit offsets. As 32-bit offsets, they would take 67 MB
     instead of 134 MB with 2^22 vertices.

   Both are proper experiments for a later run.
4. **Checking a "yes" certificate is faster than the plain test.**
   - On the grid, checking takes 0.69–0.75× the time of the plain test with DFS, and 1.27–1.38×
     the time of the DFS alone.
   - On G(n,m) + cycle, it takes 0.29–0.63× the time of the plain test with DFS, falling with
     size. From 2^19 vertices on, checking is faster than the DFS alone: 0.47× its time with
     2^22 vertices.
   - On these certificates, the two checkers take the same time within 6 %. They run the same
     code, which differs only in whether an ear may start and end at the same vertex.

   A guess, not yet checked: the checker reads the graph's lists in order, and then the ears in
   order. Its random accesses go to per-edge and per-vertex arrays at positions that come from
   the certificate, so they do not depend on each other, and the CPU can wait for several cache
   misses at once. In the DFS, each step depends on the memory access before it. This needs
   counters of memory-level parallelism, which this machine does not give the benchmarks.
5. **Checking the "no" certificates of this run is almost free, but tells little.** Each
   certificate is a single vertex, so the checker reads at most one list. Its time grows with n
   (0.17 µs with 2^14 vertices, 50 µs with 2^22) because it first clears one byte per vertex. A
   class whose smaller side is large, for example two random graphs joined by a single edge, would
   measure the checker on "no" certificates properly.
